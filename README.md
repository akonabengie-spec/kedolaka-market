# KEDOLAKA MARKET

KEDOLAKA MARKET is a PNG marketplace prototype served by Express. PostgreSQL stores accounts, vendor applications, listings, carts, orders, and payment state. Vendors choose their own offline payment methods and customer-facing instructions during registration or application and may update them later. Mixed-vendor carts become separate orders. A vendor may attest to receipt only for its own order; this attestation is not independent verification by a bank or payment provider. No online payment gateway is integrated.

The visual identity uses a custom crossroads-and-basket SVG logo. `assets/kedolaka-market-logo.svg` is the full lockup, `assets/kedolaka-market-compact.svg` is the compact header mark, `assets/kedolaka-market-logo-light.svg` is intended for dark backgrounds, and `assets/kedolaka-market-icon.svg` is the square app/favicon icon.

## Requirements

- Node.js 20 or newer and npm
- PostgreSQL 14 or newer
- `psql` available on `PATH`
- Nodemailer 10 is used for optional SMTP password-reset delivery; its SMTP API is exercised against a local test server and no real email is sent during tests.

## Install and run

```powershell
npm install
createdb kundu_market
psql -d kundu_market -f server/postgres-schema.sql
if (-not (Test-Path .env)) { Copy-Item .env.example .env }
```

Edit `.env`: set `DATABASE_URL`, set `TEST_DATABASE_URL` to a separate disposable database, and replace `JWT_SECRET` with a unique value of at least 32 characters. Never reuse the development or production URL for tests. Generate a secret with:

```powershell
node -e "console.log(require('node:crypto').randomBytes(48).toString('base64url'))"
```

Then run:

```powershell
npm run db:migrate
npm start
```

Open `http://localhost:3000`. The Express server serves the page routes and API from one origin. `npm run dev` uses Node's watch mode.

The website remains available in browsers, and the planned store app target is Android through Google Play only. The site includes an installable Progressive Web App (PWA) foundation with an offline shell; product, account, cart, and order data still requires an internet connection. On mobile standalone launches, the marketplace displays a compact startup screen with a progress indicator while its initial data loads. The PWA foundation is not itself a Google Play release. A Play Store package and signed Android release build still need to be prepared against the final public HTTPS website address.

## Production deployment preparation

The repository is configured for Vercel's Node.js function in `api/index.js`. Connect this Git repository to a Vercel project and deploy from the repository root. `vercel.json` packages the HTML pages, CSS, JavaScript, app assets, and existing `uploads/` product images with the function. Vercel's filesystem is not persistent, so configure Supabase Storage for new product image uploads rather than relying on local writes.

Create a Supabase project and run [`supabase/storage.sql`](./supabase/storage.sql) in its SQL Editor to create/update the public `product-images` bucket. This bucket allows public reads for product photos, restricts file types to JPEG, PNG, and WebP, and caps file size at 4 MB. The application uses the Supabase service-role key only in server-side uploads; never add it to browser code or commit it.

In Vercel Project Settings → Environment Variables, set these values for Production (and Preview if those deployments should use a separate test database):

| Variable | Value |
| --- | --- |
| `NODE_ENV` | `production` |
| `JWT_SECRET` | A unique random value of at least 32 characters |
| `DATABASE_URL` | Supabase PostgreSQL transaction-pooler connection string |
| `PGSSLMODE` | `require` |
| `PG_POOL_MAX` | `1` |
| `SUPABASE_URL` | Supabase project URL |
| `SUPABASE_SERVICE_ROLE_KEY` | Supabase service-role secret |
| `SUPABASE_STORAGE_BUCKET` | `product-images` |
| `APP_BASE_URL` | `https://kedolaka-market.vercel.app` |
| `SMTP_HOST` | `smtp.gmail.com` |
| `SMTP_PORT` | `587` |
| `SMTP_SECURE` | `false` |
| `SMTP_USER` | Gmail sender address |
| `SMTP_PASSWORD` | Google App Password; mark as sensitive |
| `MAIL_FROM` | The same Gmail sender address |

Keep `TEST_DATABASE_URL` out of Production. Use Supabase's transaction-pooler connection string for Vercel and ensure its password is URL-encoded. Vercel does not provide email delivery itself; this setup uses Gmail SMTP. Enable 2-Step Verification for the Gmail account, create a Google App Password, and use that app-specific password (not the normal Google account password) for `SMTP_PASSWORD`. In Vercel, add it as a sensitive Production environment variable; never commit it or place it in browser code. The configured sender is `akonabengie@gmail.com`; use that same address for `SMTP_USER` and `MAIL_FROM`. `APP_BASE_URL` ensures reset links use the canonical production URL. If it is omitted on Vercel, reset links fall back to the HTTPS deployment URL from `VERCEL_URL`. Redeploy after changing Vercel environment variables. `CORS_ORIGINS` is only needed for additional cross-origin frontends; same-origin Vercel requests are supported. Cloudinary remains an optional fallback if `CLOUDINARY_CLOUD_NAME` and `CLOUDINARY_UPLOAD_PRESET` are configured.

Before the first production deployment, back up the database. From a trusted machine with the Production `DATABASE_URL`, run `npm run db:setup` once for a new Supabase database, or `npm run db:migrate` for an existing compatible database. These commands modify the target database; do not point them at a test database by mistake. The messaging feature requires migration `008_buyer_vendor_messaging.sql`; apply it with the other migrations before using Messenger. After deployment, open `/health` and verify the database and schema are healthy, then test a vendor product-image upload and confirm its saved URL uses the Supabase project host. To verify password recovery, request a reset for an account you control and confirm the email arrives with a link to the production HTTPS domain; reset links expire after 30 minutes and can only be used once. Keep payment-provider settings disabled until real provider onboarding and verification are complete.

The Android Play Store package cannot be generated until the website has a stable public HTTPS URL. After deployment, use that URL for the Android Trusted Web Activity and publish the matching Digital Asset Links file at `/.well-known/assetlinks.json`. This workspace currently has Java 8 and no Android SDK configured; Android release builds require a supported modern JDK and Android SDK. Keep the Android signing key private and backed up; never commit it or send it in chat.

## Pages and navigation

The customer journey uses `/` (marketplace), `/products` (search, category, price, and sort filters), `/product-detail.html?id=...`, `/cart.html`, `/checkout.html`, `/order-confirmation.html?ids=...`, `/orders.html`, `/order-detail.html?id=...`, `/payment-status.html?id=...`, `/account.html`, and `/messenger.html`. Any signed-in account can start a conversation with an active vendor; buyers, vendors, and administrators can view and reply only to conversations they participate in. Sign-in and recovery use `/login.html`, `/register.html`, `/forgot-password.html`, and `/reset-password.html?reset=...`. Vendor operations use `/vendor-application.html`, `/vendor-dashboard.html`, `/vendor-products.html`, `/vendor-product-form.html` (add or edit using an optional product `id`), and `/vendor-orders.html`. Administration uses `/admin-dashboard.html`, `/admin-vendors.html`, `/admin-products.html`, `/admin-orders.html`, `/admin-freight.html`, `/admin-payments.html`, and `/admin-audit.html`. `/help.html` is the support destination; navigation and product search are shared across the marketplace.

On mobile, the Home page header places a friendly welcome above the product search; other pages keep their own search and filters without a duplicate header search. A fixed bottom bar provides Home, Categories, Messenger, Cart, and My Account. The profile page groups account shortcuts, support, dark mode, and sign-out; desktop navigation remains unchanged.

For compatibility, `/auth.html` and `/auth-flow.html` display the sign-in page; old `/auth.html?reset=...` links redirect to the dedicated reset page. `/my-orders.html` aliases the order list, `/vendor-workspace.html` and `/vendor-dashboard.html` open the vendor dashboard, and `/admin.html` and `/admin-workspace.html` open the admin dashboard. Legacy About, category, and search-result URLs redirect to `/products`; `/contact.html` redirects to `/help.html`. Unknown HTML paths return the 404 page.

Express redirects unauthenticated requests for cart, checkout, account, order, vendor, and admin pages to sign-in with a same-origin return path. Vendor pages require the vendor role, and product/fulfillment management pages additionally require active approval. Admin pages require the admin role. The API independently enforces authentication, role, vendor approval, and record ownership; page-level checks are not a substitute for those API checks. Run `npm test` for unit tests, PostgreSQL API/access-control integration tests, page/asset/route checks, and Chrome-based browser tests of product discovery, search and filters, product details, error recovery, legacy redirects, and responsive layouts.

The PostgreSQL schema is `server/postgres-schema.sql`. The old `server/db-schema.sql` is a MySQL-era schema and is not used by this application. The schema file uses `CREATE TABLE IF NOT EXISTS`; it creates a new database layout but does not migrate existing tables. Versioned, transactional SQL migrations live in `server/migrations/`; `npm run db:migrate` records and applies unapplied migrations while holding a PostgreSQL advisory lock. Migrations 001–004 provide checkout idempotency, administrative audit, payment reservations and vendor-owned payment settings. Migration `005_product_delivery_type.sql` adds delivery, pickup, or both as a per-product vendor setting, preserving existing listings as delivery-or-pickup. Migration `006_product_customer_details.sql` adds condition, price unit, and customer-facing delivery notes, with safe defaults for existing products. Migration `007_shipping_refunds_admin_operations.sql` adds manually entered shipment details and immutable admin refund records. Migration `008_vendor_payment_reference_contacts.sql` adds per-order payment-reference contacts and backfills bank/mobile-wallet methods from vendors' existing valid PNG phone numbers. Migration `009_product_fulfillment_details.sql` adds structured product specifications and delivery information; existing products keep empty details until vendors edit them. Migration `010_product_province_delivery_contacts.sql` adds private local driver/skipper contacts and order-item contact snapshots. Migration `011_province_route_transport.sql` adds the ship provider for inter-province freight. Migration `012_disable_legacy_postpng_rates.sql` deactivates legacy PostPNG freight rates now that inter-province checkout uses ship or air freight. Migration `013_delivery_payer_pmv_driver_details.sql` records whether the buyer or vendor pays delivery and stores the vendor-entered PMV driver and vehicle details. Migrations do not reset or recreate the database. Back up existing data and review migrations before applying them to a production database.

Startup checks PostgreSQL connectivity and verifies that the active schema's required tables and columns exist. The health endpoint reports an incomplete schema as unhealthy; the app does not run migrations or modify database contents automatically at startup.

## Configuration and operations

- Same-origin requests are allowed automatically. `http://localhost:<port>`, `https://vercel.app`, and `https://kedolaka-market.vercel.app` are allowed by default; set `CORS_ORIGINS` to a comma-separated list of exact additional browser origins when the frontend and API use different origins. Include the full deployment host (for example, `https://your-project.vercel.app`) if using another Vercel subdomain.
- In production set `NODE_ENV=production`, use HTTPS, a managed secret, and PostgreSQL TLS settings (`PGSSLMODE=require`).
- Supabase setup: set `DATABASE_URL` to the PostgreSQL transaction-pooler connection string and `PGSSLMODE=require`; set `PG_POOL_MAX=1` on Vercel. For a new database run `npm run db:setup` once; for an existing database run `npm run db:migrate`. Back up any existing production database before migrating its data to Supabase; schema migrations alone do not copy records. This keeps the app's existing application-managed sign-in; Supabase Auth is not enabled. Run [`supabase/storage.sql`](./supabase/storage.sql) to provision the public `product-images` bucket, then set `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY`, and `SUPABASE_STORAGE_BUCKET` in the server environment. The service-role key is secret and must never be placed in browser code. New uploads use Supabase Storage when configured; without it, existing Cloudinary configuration remains the fallback. Existing Cloudinary and local `/uploads/...` image URLs continue to work; the tracked local product images are also included in Vercel's function bundle.
- Create an administrator only through a trusted database operator after verifying the account identity, for example: `UPDATE users SET role = 'admin' WHERE email = 'operator@example.com' AND role <> 'admin';`. Public registration never accepts the `admin` role. The separate administrative tools are served under `/admin-*.html`; page and API authorization are enforced server-side.
- Vendor accounts begin with `review` status. Registration requires the business name, province, and at least one selected payment method with public customer instructions. Bank transfer and mobile wallet methods also require a valid PNG phone number or WhatsApp number where buyers can send payment references. For bank transfer, vendors can enter account names and numbers for BSP Bank, Kina Bank, or both, plus an optional customer-facing note. For mobile wallet, vendors provide the provider, account name, wallet number, and an optional note. The supported methods are bank transfer, mobile wallet, cash on delivery, and in-person payment; they are manual/offline methods, not gateway integrations. Vendors can select multiple methods and change these settings in their dashboard. Customers choose one configured method per business at checkout; the chosen reference contacts are snapshotted onto each order. Administrators can approve, reject, or suspend applications. Approved vendors can manage their own listings and fulfill their own orders; administrative state changes are recorded in `admin_audit_logs`.
- Approved vendors must provide a detailed product description (at least 20 characters), condition, price unit, province, delivery type, brand, model/SKU, size/dimensions/weight, materials/ingredients, origin, warranty/returns, service areas, preparation/dispatch time, estimated delivery time, pickup arrangements, and delivery restrictions. Enter “Not applicable” or an equivalent when a specification does not apply. Delivery listings require a local driver/skipper name, PNG mobile number, vehicle/boat/provider, and route/pickup/drop-off point for deliveries within the product's province. Pickup-only listings do not need a local transport contact. Within-province delivery uses PMV and requires that contact; another province requires ship or air freight instead, and local driver/skipper details are not shown on those orders. A selected local contact is snapshotted to the order and shown only to that order's buyer and vendor after checkout; it is not included in public product listings or cart data. Vendors can also add a clear HTTPS product photo and extra customer-facing delivery/pickup notes. Customers can see the public product specifications and fulfillment information on product detail pages. Delivery charges continue to come from configured freight rates at checkout; vendors should not add them to product prices. Checkout disables methods that conflict with the selected province route, and the API rechecks compatibility. Buyers enter their address, province, and phone at checkout; their registered name and checkout delivery details are shared with the relevant vendor for fulfillment.
- Checkout lets the buyer choose whether the buyer or vendor pays configured delivery charges. If the vendor pays, the freight cost remains recorded on the order but is excluded from the buyer's payment total. For PMV orders, the vendor must enter the assigned driver's name and PNG phone number, vehicle plate number, and vehicle description when recording shipment details; these are then visible on that order to the buyer.
- No freight rates are seeded because verified PNG carrier rates were not provided. Configure route/provider estimates in the database or through the admin freight endpoint. Rates default to `is_estimate = true` and are shown as estimates; checkout is unavailable for routes without a configured rate. The cart can request a quote for the configured rates across its seller provinces and checkout recalculates those rates server-side. Freight is one configured rate per distinct seller province for the selected destination and provider; it does not infer weight-based fees.
- Password reset email is enabled only when SMTP variables in `.env` are configured. Without them the endpoint explicitly returns `503 email_unavailable`; failed SMTP delivery does not claim success. SMTP delivery has not been verified in this environment.
- Help and contact pages use `js/pages/support-contact.js` for public support contact details. Set the `supportContact` email, phone, WhatsApp, and hours values there; blank values stay hidden from customers.
- Vendors can upload JPEG, PNG, or WebP product images up to 4 MB; signatures are checked and images are uploaded to Supabase Storage when configured, with Cloudinary as an optional fallback. The 4 MB limit keeps multipart requests within Vercel's function request-body limit. HTTPS image URLs remain supported. Existing `/uploads/...` links are served from the bundled local images when present; new uploads must use remote storage on Vercel because its filesystem is not persistent.
- Vendors can manually enter carrier, booking reference, tracking number/link, and notes after packing. No carrier booking API, label purchase, scan synchronization, or delivery confirmation integration is present; tracking links are vendor-supplied HTTPS URLs.
- Administrators can correct delivery address/province/phone/shipping method, view operational metrics, and record partial or full offline refunds with a method, reason, and optional reference. Order totals and original payment records are not edited. Refund records do not transfer money; the administrator must perform the offline transfer separately. Refund history is immutable and audited.
- The vendor-specific checkout presents only methods stored for each business and validates every selection again on the server. A mixed-vendor cart is split into one independently priced and freight-calculated order per vendor. Payment instructions are snapshotted onto each order so later vendor edits do not change existing orders. Never accept card numbers or CVVs in this application.
- `PAYMENT_SANDBOX_ENABLED=true` enables a test-only pending order record outside production. Production startup rejects this setting. A sandbox record never charges or verifies money.
- Vendors supply their own payment instructions, which are displayed to customers. Instructions must not contain passwords, card details, or account-security credentials. Vendor receipt confirmation is scoped to that vendor's order and is recorded as a vendor attestation with an optional receipt reference; it does not represent independent bank/provider verification. The existing admin verification workflow remains available for authorized manual review. Sandbox test records remain pending and never charge or verify money.
- `PAYMENT_RESERVATION_MINUTES` and `PAYMENT_MANUAL_RESERVATION_MINUTES` govern sandbox and legacy marketplace payment records; configuration is validated at startup. They do not replace a vendor's selected customer-facing payment instructions.
- Migration `003_payment_reservations_manual_verification.sql` does not backfill reservations or change stock for existing orders. Review outstanding pre-migration pending orders and reconcile them using trusted records before rollout; do not infer that money was received.
- `PAYMENT_RESERVATION_MINUTES` (5-1440, default 30) controls sandbox reservation length. `PAYMENT_MANUAL_RESERVATION_MINUTES` (5-10080, default 1440) controls pending manual orders. Reservations are released on cancellation or expiry. For prepaid manual orders, stock is consumed only after the vendor attests to receipt (or an administrator verifies it). COD fulfillment may proceed while payment is pending; stock is consumed at dispatch, its reservation is no longer held, and the vendor can confirm collected cash after delivery. Payment statuses distinguish pending from a vendor-attested receipt.

## Tests

The API integration and browser tests require a separate disposable PostgreSQL database with the current migrations applied. A preflight refuses to run unless `TEST_DATABASE_URL` names the designated `kundu_market_test` database and its schema passes the read-only health check. Never point `TEST_DATABASE_URL` at a production or customer database. The browser suite also requires Google Chrome; install it separately if unavailable.

```powershell
createdb kundu_market_test
psql -d kundu_market_test -f server/postgres-schema.sql
$env:TEST_DATABASE_URL = 'postgresql://postgres:change-me@localhost:5432/kundu_market_test'
npm test
```

Use `npm run test:unit` for payment configuration, disabled-provider, and local SMTP transport checks; `npm run test:api` for the PostgreSQL integration suite and route/asset/access checks; and `npm run test:e2e` for the browser suite. The aggregate `npm test` runs all three and fails if the test database is absent, targets another database, or is missing a migration. API tests cover registration, duplicate rejection, password hashing, login, session revocation, authorization, vendor payment setup, vendor review and approval, product discovery, freight configuration, cart validation, idempotent single- and multi-vendor checkout, server-calculated order totals, order privacy, vendor-only payment attestations, inventory consumption, manual payment verification, forged webhook rejection, product moderation, audit activity, and schema health. Browser tests use actual PostgreSQL product/category, cart, freight and order records to verify API-calculated totals, vendor instructions, idempotent order replay, pending payment status, and checkout failure recovery. Test-only browser interception also verifies catalog failure/retry and omitted-field behavior. Cleanup targets only fixture records created by each test.

For an existing test database, apply pending migrations and run the suite with:

```powershell
$env:DATABASE_URL = $env:TEST_DATABASE_URL
npm run db:migrate
npm test
```

Back up PostgreSQL with `pg_dump -Fc -d kundu_market -f kundu_market.backup` before production schema changes. Restore into a new database with `createdb kundu_market_restore` and `pg_restore -d kundu_market_restore kundu_market.backup`; validate the restored database before switching traffic.

## API outline

- `POST /api/auth/register`, `POST /api/auth/login`, `POST /api/auth/logout`, `GET /api/auth/me`, `GET /api/auth/session`
- `POST /api/auth/forgot-password`, `POST /api/auth/reset-password`
- `GET /api/products` (supports `q`, `category`, `province`, `minPrice`, `maxPrice`, `sort`, `limit`, and `offset`), `GET /api/products/categories`, `GET /api/products/:productId`
- `GET /api/cart`, `PUT /api/cart/items/:productId`, `DELETE /api/cart/items/:productId`
- `POST /api/orders`, `GET /api/orders`, `GET /api/orders/:orderId`, `POST /api/freight/estimate` (one origin or `originProvinces` for a cart quote)
- `POST /api/checkout` requires an `Idempotency-Key` UUIDv4 header and a vendor payment selection per cart business; server-calculated totals and freight are split into vendor orders. Safe retries return the existing orders, while reuse with different request/cart data is rejected.
- `POST /api/orders` remains as a single-vendor compatibility route; it refuses mixed-vendor carts and validates manual payment methods against that vendor's settings.
- `GET /api/payments/methods` returns only server-configured payment choices. No live gateway callback route exists until a provider's official verification contract is implemented.
- `POST /api/orders/:orderId/cancel` releases a buyer's still-pending order reservation.
- Admin-only: `POST /api/admin/payments/:paymentId/verify` records an authorized human's manual success/failure review and receipt reference.
- Vendor-only: `POST /api/uploads` (multipart `productImage`; returns Cloudinary `secure_url`), `POST /api/vendor/profile`, `PATCH /api/vendor/payment-methods`, `GET /api/vendor/dashboard`, `POST/PATCH/DELETE /api/vendor/products` (multipart product images supported), `POST /api/vendor/orders/:orderId/payment-confirmation`, `PATCH /api/vendor/orders/:orderId/status`, `PATCH /api/vendor/orders/:orderId/shipment`
- Admin-only: `GET /api/admin/dashboard` (including operational metrics), `PATCH /api/admin/orders/:orderId` (delivery/contact fields only), `POST /api/admin/orders/:orderId/refunds` (manual refund record), `PATCH /api/admin/vendors/:vendorId/status`, `PATCH /api/admin/products/:productId/status`, `POST /api/admin/freight-rates`
- `GET /health` reports application and PostgreSQL availability.

## Verified capabilities and remaining integrations

The application uses database-backed customer accounts, listings, carts, orders, vendor-owned payment setup, vendor fulfillment, vendor review, freight quotes, manual payment attestations, expiring stock reservations, Cloudinary product-image uploads, manual shipment details, manual refund records, limited admin delivery edits, and operational analytics. No product or freight data is seeded. BSP IPG, Kina Bank IPG, Digicel/MyCash merchant payments, card processing, automatic provider verification, carrier booking/tracking integrations, shipping label purchase, and provider-side refund execution are not integrated. No provider sandbox or live transaction was tested. Admin order edits do not change financial totals; manual refund records do not move money.
